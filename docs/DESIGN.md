# Design: patient record linkage pipeline

_Status: agreed 8 November 2026, before implementation. Decisions are recorded with the reason and the alternatives considered, so later changes can be judged against them._

## 1. Problem
Health systems hold the same person under several records: a typo at registration, a changed surname, a missing date of birth, a different hospital. Duplicates split a patient's history and distort counts. Wrongly merging two people is worse, because one patient's history can then appear on another's record.

This project builds a repeatable pipeline that takes messy patient records from several sources, checks their quality, links them with probabilistic matching, and gives each person a stable identifier. It also measures how accurate the linkage is, including for which groups it works less well.

**Why it matters for this portfolio:** record linkage is the strongest skill on the CV, but that work used confidential data. This project shows the same skill in public on synthetic data.

**What it does not prove:** the 99.8% deduplication figure from professional work. Accuracy here depends on how much error is injected, so results are reported at several error levels and are not presented as comparable with that figure.

## 2. Scope
**In scope:** synthetic source systems with injected errors and known truth; a PostgreSQL warehouse; data-quality gates; Splink linkage compared with a deterministic baseline; clustering and stable person IDs; a clerical review queue; incremental loads orchestrated by Airflow; one PySpark step; a BI layer; documentation.

**Out of scope:** real patient data; a user interface for clerical review; high availability; cloud deployment (it runs locally in Docker, and Phase 4 can revisit this).

## 3. Data
- **Base population:** patients generated by [Synthea](https://github.com/synthetichealth/synthea) (Apache-2.0), run in Docker because Java is not installed on the VM. The run is pinned by version, seed and reference date.
- **Three simulated source systems,** such as hospital, GP and laboratory, each holding a subset of people with different fields and quality.
- **An error injector written for this project,** seeded and tested: typos, nicknames, transposed names and date digits, missing values, changed surnames, house moves and duplicates within a source.
- **Three error levels** (low, medium, high). The rates are illustrative choices recorded in the config and are not estimates of real-world error.
- **Truth is known,** because the injector records which person each record came from. The truth table is held apart from the pipeline and used only for evaluation.
- **Identifier:** a synthetic NHS-style number, present on only some records and sometimes wrong, as in real data. Step 2 will confirm the numbers come only from the range reserved for testing.
- **Limitation:** Synthea's names and addresses are American, so name patterns differ from the UK's.

## 4. Architecture
```
 Synthea + error injector ──► source files (3 systems, daily batches)
                                      │  Airflow DAG (LocalExecutor, Docker)
                                      ▼
 PostgreSQL:  raw ──► staging ──► data-quality gate ──(fail)──► stop and report
                                      │ pass
                                      ▼
 Splink on DuckDB: blocking ──► scoring ──► clustering
                                      │
                                      ▼
 PostgreSQL:  person_id map (stable) · review queue · marts ──► Power BI

 Evaluation (kept out of the pipeline): results + truth table ──► precision, recall, F1, by group
```

## 5. Evaluation
Rules are fixed here, before any results exist.

- **Baseline:** deterministic rules (exact identifier, then exact surname, first name and date of birth). Splink has to be worth its extra complexity.
- **Metrics:** pairwise precision, recall and F1, plus cluster-level measures: the share of people with several records who are split across clusters, and the share of all people placed in a cluster with someone else.
- **False merges are treated as the more serious error,** so thresholds are chosen for high precision and recall is reported alongside.
- **Three independent populations by seed:** one for training the model, one for choosing thresholds, and one used **once** for final results.
- **Threshold rule:** on the tune population, use the lowest swept threshold reaching 99.5% pairwise precision. This target was set before any linkage had been run. The test population then gets that threshold, and the code refuses a second final run or a threshold chosen on the test data.
- **The 1,145-person pilot is for building the code only.** Nothing measured on it is reported as a result.
- **Training does not use truth.** Splink's parameters are estimated unsupervised, as they would have to be on real data.
- **Fairness:** error rates by sex, age band and ethnicity, because linkage errors are known to fall unevenly across groups and can bias later analysis.
- **Sensitivity:** results at all three error levels.

## 6. Decisions

| # | Decision | Why | Alternatives considered |
|---|---|---|---|
| D1 | Splink 5.0 | Open-source, from the UK Ministry of Justice, used across UK government. Version 5 was tested on this VM before this design was written | fastLink (R only); hand-written Fellegi-Sunter (reinvents a solved problem); dedupe (needs active labelling) |
| D2 | Splink runs on DuckDB, reading from and writing to PostgreSQL | Fast and memory-efficient on one machine | Splink's PostgreSQL backend (slower); Spark backend (too heavy for 7.3 GB) |
| D3 | Airflow 3.3.2 with LocalExecutor | Airflow appears in Data Engineer adverts. 3.4.0 was only two days old at design time, and LocalExecutor avoids Redis and Celery workers | Airflow 3.4.0 (too new); CeleryExecutor (memory); cron (no retries or dependency handling) |
| D4 | One PostgreSQL container with separate databases for Airflow and the warehouse | Saves memory on a small VM | Two containers |
| D5 | Data-quality checks are SQL plus pandera, and a failure stops the run | Small, testable and easy to explain | Great Expectations (heavy for a 7.3 GB VM) |
| D6 | Stable person IDs kept in a mapping table across runs | Splink's cluster IDs change between runs, and downstream users need an ID that does not | Exposing cluster IDs directly |
| D7 | Full re-link is the default. Incremental linkage is added only if Splink 5's experimental `predict_between` proves reliable in testing | Avoids depending on an experimental feature | Incremental linkage from the start |
| D8 | PySpark limited to one standardisation job in local mode, outside the nightly path | Gives real PySpark evidence without overloading the VM | Spark throughout; leaving it out (Spark is a known gap) |
| D9 | Power BI built on the Windows host from exported mart files, with screenshots and the `.pbix` committed | Power BI Desktop is Windows-only | Superset or Streamlit (Power BI is what NHS adverts ask for) |
| D10 | PostgreSQL 17, pinned by digest (added in step 3) | Airflow will share this server in step 6, and the older major version is the more cautious choice. Confirmed working with Airflow 3.3.2 in step 6 | PostgreSQL 18 |
| D11 | Airflow runs as one `standalone` container, capped at 3 GB (added in step 6) | Fits the VM with room for linkage. It is a development mode, so a real deployment would run the components separately | Separate scheduler, API and DAG-processor containers (more memory) |
| D12 | The project has its own virtual environment inside the Airflow image (added in step 6) | Airflow's pinned packages and the project's differ, for example pandas 3.0.5 and 3.1.1. Tasks call the project's commands | Installing both together (version conflicts) |
| D13 | One failed run pauses the DAG, and the loader refuses a day whose previous day is missing. `depends_on_past` is not used (added in step 6, **after testing**) | With `depends_on_past` and one run slot, the next day started, waited on the failed day and held the slot, so a cleared day could never run. Clearing later days did not help, because their tasks had no state to clear | `depends_on_past` (deadlocks recovery); more run slots (the waiting runs fill those too) |
| D14 | The quality gate judges each batch separately, and a share can only fail with at least 5 affected records (added in step 6) | Across a whole dataset one bad day is diluted. Small daily batches also make single bad values look like large shares | Whole-dataset checks; raising every threshold |
| D15 | A failed batch keeps its check results but none of its data (added in step 6) | Corrected files reuse record IDs, so rows from a failed load would block the correction for good | Upserting raw rows (raw would no longer be as received) |

## 7. Machine limits
The VM has 4 cores and 7.3 GB of RAM. Measured in step 6, Airflow uses about 1.0 GB idle and peaked at 1.4 GB while processing the pilot, leaving about 2 GB available, with no out-of-memory events. At full size (about 11,500 people and 27,000 records), one linkage run peaked at about 670 MB and took about 20 seconds, so the population did not need shrinking. Airflow's memory at full size is still unmeasured.

## 8. Cost
**£0.** Everything runs locally and all the tools are open source. No cloud resources are created.
